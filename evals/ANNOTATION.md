# 标注口径与标签审计（intent label audit）

本文件是 `evals/*.jsonl` 里 `expect.task_type` 的**判定依据**，也是"为什么这些标签可以信"的证据。
它存在的理由：评测的第一个失败模式不是引擎判错，而是**标注员自己标错**，于是 60% 这种数字会被读成准确率。

- 口径版本：v1.1（2026-10-04，Asia/Shanghai；v1 → v1.1 的修订理由见 §2.1 修订记录）
- 适用集合：`inputs.local.jsonl`（真实 20 条）、`dev.jsonl`、`samples.jsonl`、以及后续所有新集合
- 相邻文档：命令与基线对照见 `evals/README.md`；引擎侧的意图本体见 `docs/prompt-optimizer-plugin-design.md` §2

---

## 1. 标注口径（按顺序判定，先命中者胜）

tag 回答的是**"用户想让 AI 交出什么"**，不是话题、不是难度。

| 标签 | 判据（命中即采用） | 典型触发词 |
|---|---|---|
| `converse` | 没有实质请求（寒暄、试音、纯情绪无问题） | 在吗、谢谢 |
| `decide` | 在**≥2 个已点名的选项**里选一个 | "maven 和 gradle 选哪个"、"该不该用 X" |
| `code` | 交付物是**代码/SQL/配置文本本身**，或对已有代码生成/改写/优化/补全。**例外**：若诉求是**问成因**（"是哪里错了"、"是配置问题还是框架不支持"、"为什么会这样"），不是要改法 → 不判 code | "写/生成/改成…写法"、"怎么改这个报错" |
| `transform` | 交付物是**已有文本**的改写/压缩/润色/翻译/换语气/转格式（原文带着被加工的文字） | "回得客气点"、"压缩一下" |
| `extract` | 从给定材料里抠出**信息条目** | "挑出来"、"提炼"、"汇总成表" |
| `review` | 对给定材料**挑错/核对/找漏洞** | "审一下"、"核对一遍"、"有没有问题" |
| `plan` | 交付物是**可执行的步骤/时间表/清单/方案设计** | "怎么排查"、"怎么办"、"有啥手段"、"从哪查起" |
| `learn` | 交付物是**通用概念/原理/用法差异的解释**，不要求可执行步骤，且**不含**"某现象/某差距为什么会这样"的成因追问 | "啥意思"、"啥区别"、"怎么实现的" |
| `analyze` | 交付物是**对已观察到的现象/现场或差距的归因或判断**——可以是具体现场（这次报错、线上挂了），也可以是**普遍现象**（"为什么国内公司宁愿改开源 JDK"） | "咋回事"、"为什么挂了"、"什么情况" |
| `write` | 从零产出新文本（无素材，也不是代码） | "写个文案" |

## 2. 关键边界（最容易标错的地方）

| 边界 | 判定 |
|---|---|
| analyze vs learn | analyze 针对**已观察到的现象/现场/差距**（我这行代码、这次报错、线上挂了、"为什么 X 普遍不如 Y"）；learn 问**通用概念/机制/定义**（"== 和 equals 区别"） |
| — 例 | "这个报错啥意思" → **learn**；"这个空指针咋回事，我明明判断了 null" → **analyze** |
| analyze vs plan | 问"原因/为什么/咋回事" → analyze；问"怎么排查/怎么办/有啥手段/从哪查起" → **plan** |
| code vs analyze vs plan（报错类先看诉求） | 要**改动后的产物/改法** → code；要**原因** → analyze；要**排查步骤** → plan。例："报错 XXX 怎么改" → **code**；"报错…是哪里配置错了还是框架不支持" → **analyze** |
| plan vs learn | "一般咋做/怎么做" → plan（要可执行做法）；"原理/为什么" → learn |
| decide vs plan | 有明确候选集合二选一 → decide；问"该怎么落地/有什么方案" → plan |

### 2.1 修订记录

- **v1 → v1.1（2026-10-04）**：触发来自第二留出集（`holdout2.jsonl`）的两条判错——v20「单测启动报错…**是哪里配置错了还是框架不支持**」被判 `code`（应 analyze）；v15「通用 agent **为什么**比不过专用的」被判 `learn`（应 analyze）。
  这两条暴露的是 **v1 表述歧义**，不是新增口径：① `code` 的命中条件本来就是"要改法"，不能见到「报错」就命中；② `analyze` 的"具体现象/现场"应读作"**已观察到的**现象"，**普遍现象的成因也属归因**。
- **验证纪律**：v1.1 的效果只能在**修订后新采集、从未跑过**的集合（`holdout3.jsonl`）上验证；`holdout2`、`holdout`、`inputs.local`、`samples`、`dev` 均已消耗，**不得**用于证明本次修订有效。
- **回滚条件**：若 `holdout3` 上 `code` 的召回明显下降（把"报错求解决"误判成 analyze/plan），则说明例外写得过宽，须收窄为"仅当问句本身是成因判断句（是…还是… / 为什么）时让位"。
- **回滚已触发（2026-10-04）**：`holdout3`（w01–w20）实测严格 70.0% / 宽松 90.0%，但 `code` 主标签 4 条只判对 1 条（w05「pom.xml 该如何配置」、w16「想做个程序实现…怎么弄」都被判 `plan`）→ 按上式把例外**收窄为"仅当问句本身是成因判断句时才让位"**（写在 `src/llm/analyze.js` 的 `code` 行，记为**引擎侧 v1.2**）。
- **v1.2 是引擎强调问题，不是判据修订**：第 1、2 节的判据（`code` 交付物是配置/代码文本、`decide` 含"该不该选 X"）**一字未改**；改动只在 `src/llm/analyze.js` 的 `TASK_GUIDE` 与判断纪律里补正例与反例。理由：holdout4 的 A 臂显示模型不是"判据没有"，而是"强调不足"（配置类被判 plan/learn、判断类被判 learn）。
- **验证纪律（v1.2）**：v1.2 是在看过 `holdout4` A 臂错误之后写的，因此它在 `holdout4` 上的数字属**样本内**，只能证明方向；干净的泛化数字必须来自 `holdout5.jsonl`。

## 3. 多标签：承认边界，但不要偷偷放宽

真实的意图在边界上是**两个都成立**的。处理方式不是删掉一个标签，也不是把阈值调松，而是显式记录可接受集合：

```jsonl
{"id":"u07","text":"急！线上服务挂了 日志里一堆 timeout 从哪查起","expect":{"task_type":["plan","analyze"]}}
```

- 数组第一个元素是**主标签**：严格口径（`意图准确率（严格）`）只认它。
- 整个数组是**可接受集合**：宽松口径（`意图准确率（含可接受替代）`）命中任一即算对。
- 报告同时给出两个数，禁止只报宽松口径。
- 使用门槛：只有在独立标注员**也**认为两可时才允许多标签；不允许事后为了救某个样本而加。

## 4. 标签变更协议（铁律）

1. 标签只能**依据本文件的判据**修改，**不得依据引擎或模型的输出**修改——否则重演 dev 集 100% 自证。
2. 修改必须走**独立标注**：另一个标注员（不同上下文、看不到原标签、看不到模型输出、只读第 1 节的判据）重新标一遍。
3. 双方分歧 → 记为主标签 + 可接受集合；三方（我 / 独立标注员 / 模型）都不同 → 标为**待人工终审**，不悄悄改。
4. 每次改标签都要留下三方对照表（第 5 节），并说明改了哪几条、依据是什么。
5. 标注员与模型同族时存在同向偏差，必须在报告里声明（本次即是）。

## 6. 留出集（`holdout.jsonl`）标注与盲标复核（2026-10-04）

**为什么需要**：`inputs.local.jsonl` 的标签已被审计过、被我看过、也被模型跑过——它已经不能回答"换一批没见过的输入还行不行"。`holdout.jsonl` 是从用户同一批 40 条候选里取出的、**从未进入任何一次调参 / 审计 / 模型运行**的另外 20 条（`h01`–`h20`）。

**协议**：与第 5 节一致——全新上下文的独立标注员，只拿到第 1–2 节判据与 20 条打乱顺序的原文；禁止读仓库、禁止猜测引擎行为、必须给出抄自原文的证据片段。

**一致率**：主标签一致 **15/20**；分歧 **5 条**（h05 / h12 / h14 / h16 / h17）。

**调解规则（一次性写死，避免逐条挑）**：双方分歧且判据不能判定谁对 → 主标签取**盲标**（独立标注员），可接受集合里保留我的第一轮标签；只有**两方都认为两可**的样本才给多标签。调解发生在看到模型判定**之前**。

| id | 我（第一轮） | 独立盲标 | 最终 | 说明 |
|---|---|---|---|---|

**双方都判两可（多标签）**：h01 `["decide","learn"]`（问区别 + 问用哪个更好）、h13 `["analyze","plan"]`（问分片是不是设多了 + 问一般几个合适）。

**覆盖度缺陷（任何报告都必须声明）**：holdout 只覆盖 analyze(4) / plan(9) / code(4) / decide(1) / learn(1) / converse(1)，**没有 write / transform / extract / review 样本**。规则层最典型的失败（无信号回退 `write`）在这里只能通过"期望不是 write 却回退成 write"暴露，无法验证 write / transform / extract / review 这几类本身。

**结论**：holdout 可作泛化证据，但其中 5 条是"盲标优先 + 待人工终审"，因此泛化数字必须**同时报严格与宽松两个口径**，并注明 5 条终审未定。
